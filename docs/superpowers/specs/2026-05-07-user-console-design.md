# `web/user-console` 用户控制台设计稿

## 1. 背景

当前 `web/default` 同时承载公开页面、普通用户页面和管理员页面。虽然已有用户能力较完整，但信息架构和视觉气质仍然偏向原生 NewAPI 后台，难以形成独立的用户端产品体验。

本次重构目标是在 `web/` 下新增一个独立前端 `user-console`，只承接普通用户能力，通过新的路由、布局和视觉系统，形成一个与默认后台前端分离的用户控制台。

参考视觉来源为 `@/Users/tono/workspace/AI/vclaw-homepage`，但不直接复制其页面结构，而是提炼其编辑感字体、暖橙/冷蓝光晕、玻璃卡片和高密度但不拥挤的产品气质，落到新的用户端中。

## 2. 目标与非目标

### 2.1 目标

1. 在 `web/user-console` 新建独立用户端应用。
2. 新用户端只承接现有页面中的非管理员能力。
3. 首版范围包含：
   - 公开首页
   - 登录后控制台首页
   - 聊天-操练场
   - 个人中心
   - 钱包管理
   - API Keys
   - Usage Logs
   - Task Logs
4. 钱包管理中移除邀请奖励相关展示与入口。
5. 用户进入新控制台后，不再感知为原生 NewAPI 后台换皮。

### 2.2 非目标

1. 本次不实现模型广场。
2. 本次不迁移任何管理员页面与管理员导航。
3. 本次不对后端 API、权限模型、计费逻辑做功能性变更。
4. 本次不删除或替换 `web/default` / `web/classic`，两者继续保留。

## 3. 范围定义

### 3.1 公开页

- `/`
  - 用户控制台首页
  - 面向未登录和已登录用户
  - 承担品牌展示、能力说明、转化与控制台导流

### 3.2 登录后页面

- `/console`
  - 控制台首页
- `/playground`
  - 聊天-操练场
- `/workspace/keys`
  - API Keys
- `/workspace/logs`
  - Usage Logs
- `/workspace/tasks`
  - Task Logs
- `/account/profile`
  - 个人中心
- `/account/wallet`
  - 钱包管理

### 3.3 明确排除

- 模型广场
- `Channels`
- `Models`
- `Users`
- `Redemption Codes`
- `Subscription Management`
- `System Settings`
- 任何管理员分析维度或管理员专属入口

## 4. 信息架构

### 4.1 一级结构

新用户端分为三层：

1. 首页
   - 品牌展示与转化入口
2. 控制台
   - 用户主要工作入口
3. 账户
   - 个人资料、安全和资产管理

### 4.2 导航分组

登录后桌面端侧边栏分为三组：

1. `Console`
   - 控制台首页
   - 聊天-操练场
2. `Workspace`
   - API Keys
   - Usage Logs
   - Task Logs
3. `Account`
   - Profile
   - Wallet

移动端采用底部主导航：

1. 控制台
2. 操练场
3. 工作台
4. 我的

## 5. 页面设计

### 5.1 公开首页

首页采用更强品牌感的产品首页结构，不复用默认前端当前的节奏。

#### 5.1.1 首屏 Hero

- 左侧：
  - 品牌主张
  - 核心价值说明
  - 主 CTA
- 右侧：
  - 控制台预览卡
  - 预览余额、最近调用、快捷进入操练场、API Key 状态

#### 5.1.2 能力区

以用户价值表达能力，不以后台功能罗列表达能力。建议聚焦：

1. 快速试模型
2. 管理密钥
3. 追踪调用
4. 管理账户与充值

#### 5.1.3 工作流说明区

用三步解释完成路径：

1. 注册 / 登录
2. 充值或创建 Key
3. 在操练场测试或通过 API 调用

#### 5.1.4 控制台预览区

使用 bento grid 展示登录后页面的关键模块缩略视图，用于连接首页与控制台。

#### 5.1.5 底部 CTA

- 未登录：
  - 注册
  - 登录
- 已登录：
  - 进入控制台
  - 打开操练场

### 5.2 控制台首页 `/console`

控制台首页定义为“用户工作台”，而不是传统后台分析页。

#### 5.2.1 顶部欢迎区

- 问候语
- 当前账户状态
- 主要动作：
  - 进入操练场
  - 创建 API Key
  - 去充值

#### 5.2.2 第一屏核心指标

保留三张高价值统计卡：

1. 当前余额 / 额度
2. 累计调用次数
3. 最近消费或最近活跃时间

只保留普通用户真正会看的指标，不展示管理员分析数据。

#### 5.2.3 第二屏工作区

- 左侧：
  - 使用趋势
  - 使用摘要
- 右侧：
  - 公告
  - API 接入信息
  - 系统状态

此区块继承现有 `Overview` 中对普通用户有价值的部分。

#### 5.2.4 第三屏快捷入口

放置到其他关键页面的快捷卡片：

1. 操练场
2. API Keys
3. Usage Logs
4. Task Logs
5. Profile
6. Wallet

### 5.3 聊天-操练场 `/playground`

操练场保留现有核心能力，但页面气质从“调试页”升级为“专业 AI 工作台”。

#### 5.3.1 桌面端布局

- 左侧：
  - 模型选择
  - 参数配置
  - 请求配置
- 中间：
  - 消息区
- 右侧：
  - 响应细节
  - 调试信息
  - SSE 观察区

#### 5.3.2 移动端布局

- 消息区为主体
- 参数区和调试区进入抽屉或分段视图
- 高级参数默认折叠，避免首屏过载

#### 5.3.3 交互要求

- 主操作明确：
  - 发送
  - 停止
  - 复制
  - 重试
- 降低边框堆叠感，提升信息层次清晰度

### 5.4 个人中心 `/account/profile`

页面围绕“账户 + 安全 + 偏好”组织，保留现有能力但重组结构。

保留：

1. 基本资料
2. 修改密码
3. 绑定邮箱 / Telegram / 微信
4. Passkey
5. 2FA
6. 语言偏好
7. 签到

页面不再呈现后台设置卡片堆叠感，而是更接近消费级产品账户中心。

### 5.5 钱包管理 `/account/wallet`

钱包页定位为“账户资产中心”。

保留：

1. 余额统计
2. 充值入口
3. 套餐购买
4. 账单 / 流水

移除：

1. 邀请奖励卡片
2. 邀请链接展示
3. 邀请奖励转余额入口
4. 邀请奖励文案

### 5.6 开发者工作台页

`API Keys`、`Usage Logs`、`Task Logs` 统一归类为工作台能力，而非散落在侧边导航中。

- `API Keys`
  - 管理凭证与接入信息
- `Usage Logs`
  - 查看通用调用记录
- `Task Logs`
  - 查看异步 / 任务型调用记录

## 6. 视觉系统

### 6.1 视觉方向

整体风格定义为：`Editorial Product Console`

核心气质：

1. 首页有品牌氛围与高级感
2. 登录后控制台清晰、专业、可信
3. 公开页与工作台属于同一产品，而不是两套断裂界面

### 6.2 字体系统

- 标题：`Space Grotesk`
- 正文与 UI：`Manrope`
- 数据与密钥片段：`JetBrains Mono`
- 中文回退：`PingFang SC` / `Microsoft YaHei`

### 6.3 色彩系统

- 主背景：`#FCFBF8`
- 主文字：`#0F172A`
- 暖色强调：`#F97316`
- 冷色强调：`#2563EB`
- 渐变强调：
  - 仅用于首页 Hero、核心 CTA、重点状态卡

### 6.4 组件与质感

- 首页：
  - 轻玻璃卡
  - 柔和背景光晕
  - 大圆角 `24-32px`
- 控制台：
  - 实体白卡为主
  - 轻玻璃为辅
  - 圆角 `18-24px`
- 表格 / 日志 / 配置区：
  - 降低装饰强度
  - 以可读性为第一优先级

### 6.5 动效

- 首页：
  - 轻量漂浮光晕
  - 分段入场
  - 卡片悬浮
- 控制台：
  - 切页
  - 悬停
  - 折叠
  - 抽屉

动效约束：

1. 时长控制在 `180-260ms`
2. 支持 `prefers-reduced-motion`
3. 不以装饰性动画干扰读写和操作

## 7. 技术设计

### 7.1 应用形态

`web/user-console` 作为独立 React 前端应用，技术栈与 `web/default` 保持同代：

1. React 19
2. Rsbuild
3. TanStack Router
4. TanStack Query
5. Tailwind CSS 4
6. Radix UI

这样可以最大限度复用现有工程经验、UI 基础设施和认证模式。

### 7.2 目录建议

```text
web/user-console/
  src/
    routes/
      public/
      authenticated/
    features/
      home/
      console/
      playground/
      workspace/
      account/
    components/
      layout/
      ui/
    lib/
      api/
      auth/
      i18n/
      format/
```

### 7.3 与 `web/default` 的职责边界

`web/default`：

1. 继续作为现有完整前端
2. 保留管理员页面与原有默认用户页
3. 本次不做结构性替代

`web/user-console`：

1. 承接新的路由层、布局层和视觉系统
2. 只面向普通用户
3. 通过迁移或抽取方式复用现有 API 调用、数据结构和部分业务逻辑

### 7.4 复用策略

不建议运行时直接跨应用深度依赖 `web/default/src/features/...` 的页面实现。

建议的复用方式：

1. 在 `user-console` 重建页面壳层、布局和样式
2. 迁移或抽取 API 请求层
3. 迁移或抽取类型定义
4. 迁移或抽取高复用业务 hooks / 格式化逻辑
5. 不复用旧页面结构与旧布局组件

原因：

1. 避免把旧页面结构和后台气质整体带入新应用
2. 降低跨应用强耦合
3. 让用户端后续独立演进更可控

## 8. 数据流与权限

### 8.1 认证

新用户端复用现有登录态与会话校验机制：

1. 公开页无需登录
2. 登录后页面在路由守卫中检查本地用户信息
3. 如存在本地登录态，首轮请求校验 session 有效性
4. 失效时清理本地状态并跳回登录页
5. 保留跳转前 URL 作为重定向目标

### 8.2 数据来源

各页面继续使用现有后端 API：

1. 首页
   - 复用现有首页内容与状态信息来源
2. 控制台首页
   - 复用现有用户概览、公告、API 信息、状态接口
3. 操练场
   - 复用现有 playground 请求链路
4. Profile / Wallet / Keys / Logs
   - 复用现有接口与业务逻辑

### 8.3 权限边界

新用户端默认只展示普通用户可见内容。

即使登录用户具备管理员角色，也不在 `user-console` 中暴露管理员导航与管理员信息架构。管理员能力仍留在 `web/default`。

## 9. 错误处理

### 9.1 全局错误

1. 路由级未登录：
   - 跳转登录页并保留重定向
2. 会话失效：
   - 清理本地状态并重新登录
3. 接口异常：
   - 页面内错误态 + 重试入口

### 9.2 页面级错误

- 首页：
  - 内容加载失败时使用默认首页结构，不白屏
- 控制台首页：
  - 模块化容错，公告异常不影响统计卡展示
- 操练场：
  - 发送失败可见、可重试
- 钱包 / Profile / Logs：
  - 局部错误态，不影响整页其余模块使用

## 10. 响应式与可访问性

### 10.1 响应式断点

至少覆盖：

1. `375px`
2. `768px`
3. `1024px`
4. `1440px`

### 10.2 可访问性要求

1. 文本对比度满足基础可读性要求
2. 所有交互元素保留可见 focus 状态
3. 动画支持 `prefers-reduced-motion`
4. 图标按钮提供可访问名称
5. 移动端触控区域不小于 `44x44`

## 11. 实施顺序

建议按以下顺序实施：

1. 应用壳层、主题 Token、认证守卫
2. 公开首页
3. 登录后主导航与控制台首页
4. 聊天-操练场
5. Profile / Wallet，并移除邀请奖励
6. API Keys / Usage Logs / Task Logs
7. 响应式、动效、i18n 与细节统一

## 12. 验收标准

### 12.1 体验验收

1. 用户端导航中不出现任何管理员入口
2. 用户感知为独立产品前端，而非后台换皮
3. 首页与控制台共享统一品牌语言
4. 登录后控制台具备清晰的一线任务入口

### 12.2 功能验收

1. 首页可正常访问
2. 登录后可进入控制台首页
3. 操练场可用于真实测试
4. Profile、Wallet、API Keys、Usage Logs、Task Logs 可正常工作
5. 钱包页不出现邀请奖励相关内容

### 12.3 工程验收

1. `web/user-console` 作为独立应用存在
2. 不破坏 `web/default` 现有功能
3. 中英文至少不破版
4. 四档断点下页面可用

## 13. 风险与约束

1. 如果直接复制 `web/default` 页面实现，后续维护成本会快速上升。
2. 如果跨应用直接深度复用旧 feature 页面，会形成强耦合并带入旧结构问题。
3. 现有用户页中部分逻辑与布局耦合，迁移时需要优先拆分“业务逻辑”和“展示层”。
4. 钱包邀请奖励虽然本次只要求移除展示，但相关接口和类型仍可能存在于业务层，需要确保只移除用户端可见部分，不误删底层能力。

## 14. 结论

本方案采用“独立用户端应用 + 复用现有非管理员业务能力”的策略，在不扰动原有后台前端的前提下，为普通用户提供新的公开首页与控制台体验。

该方案在目标、范围、结构、视觉和技术路径上均保持收敛，适合作为后续 implementation plan 的唯一基线。
