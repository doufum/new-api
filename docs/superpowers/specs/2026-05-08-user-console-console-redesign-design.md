# `web/user-console` `/console` 页面重构设计

日期：`2026-05-08`

## 1. 背景与目标

当前 `web/user-console/src/features/console/index.tsx` 已具备用户概览、快捷入口与辅助面板能力，但整体更像“卡片堆叠的入口页”，还没有形成成熟产品工作台应有的信息层级、视觉节奏与主次关系。

本次重构参考 `https://uniapi.ai/dashboard` 的内容组织思路，但不照搬其页面密度、运营语气或布局形式。目标是在保持现有数据来源不变的前提下，将 `/console` 重构为一个更精致、更有产品感的用户工作台：

- 既能承担“登录后第一屏”的欢迎与引导职责；
- 又能清晰呈现账户状态与高频操作；
- 同时把公告、帮助、API 信息、服务状态下沉为次级内容；
- 保持实现范围收敛在前端展示层，不引入新的后端接口与复杂交互。

## 2. 设计定位

页面定位为“轻运营感的产品工作台”，而不是传统后台数据大盘。

设计取向如下：

- 首屏强调欢迎感、品牌感和开始行动；
- 中段强调账户状态与高频动作；
- 下段承接说明性和辅助性内容；
- 整页看起来像成熟 SaaS 用户工作区，而不是 admin 面板或营销页。

本次设计已确认采用 `B` 方向，即 `工作台 Deck`。

## 3. 范围与约束

### 3.1 范围内

- 重构登录后默认用户入口页 `/console`；
- 调整内容结构、模块编排、视觉样式和信息层级；
- 新增少量 `/console` 专属展示组件；
- 复用现有 `SummaryCards`、`ApiInfoPanel`、`AnnouncementsPanel`、`FAQPanel`、`UptimePanel` 的数据逻辑与能力。

### 3.2 范围外

- 不新增后端接口；
- 不新增状态管理层；
- 不把 `/dashboard` 的图表分析能力迁入 `/console`；
- 不改动现有路由语义与主要目标页面；
- 不引入重型运营模块、个性化推荐或新的持久化偏好设置。

### 3.3 已确认约束

- 目标页面是 `/console`，不是 `/dashboard`；
- 本次为“内容结构 + 视觉样式”一起重做；
- 只重构前端展示层；
- 页面是混合型入口页，但必须有明确主次层级；
- `公告 / API 信息 / FAQ / 服务状态` 保留，但整体下沉到页面下半部分；
- 风格偏“产品化工作台”，不是高密度企业大盘。

## 4. 信息架构

页面采用四层结构：

1. `Hero`
2. `Summary`
3. `Actions + Support`
4. `Lower Priority Panels`

该顺序的逻辑是：

1. 先建立欢迎感与开始行动的心理预期；
2. 再让用户快速看到账户关键状态；
3. 然后承接高频操作入口；
4. 最后展示说明性和辅助性内容，避免首屏被低优先级信息抢占。

## 5. 模块设计

### 5.1 Hero

`Hero` 是首屏情绪入口，不承担全部信息展示。

职责：

- 给出欢迎语与页面定位；
- 保留品牌感，但不做重营销；
- 提供两个最强主操作；
- 在右侧给出轻量账户与状态摘要。

内容结构：

- 左侧：
  - 小型定位标签，例如 `User Workspace`
  - 主标题：强调这是用户工作台而不是纯导航页
  - 辅助说明：说明可在这里完成模型调用、额度管理与账户操作
  - 主按钮：`Open Playground`
  - 次按钮：`Open Wallet`
- 右侧：
  - 轻量账户摘要
  - 轻量状态提示

明确不放入 Hero 的内容：

- 公告列表
- FAQ
- 完整 API 信息列表
- 完整 Uptime 面板

### 5.2 Summary

`Summary` 位于 Hero 下方，保留三张核心摘要卡：

- `Current Balance`
- `Historical Usage`
- `Request Count`

职责：

- 在不引入图表的前提下回答“我的账户现在是什么状态”；
- 强化数字信息的可扫读性；
- 让用户在首屏就能建立余额、历史消耗和调用规模的基本认知。

设计要求：

- 从当前横向统计条带升级为独立卡片；
- 每张卡片保留主数字、辅助说明和轻量图标；
- 余额卡可继续保留 `Recharge` 行为入口；
- 不把这一区域做成 mini dashboard，不加入额外趋势图。

### 5.3 Quick Actions Deck

`Quick Actions` 是页面中段的核心操作区，是 `/console` 的主要功能入口层。

建议保留 4 个最高频动作：

- `Open Playground`
- `Manage API Keys`
- `Review Usage Logs`
- `Edit Profile`

说明：

- `Wallet` 已在 Hero 中承担次主 CTA，可不再强占此区位置；
- `Inspect Task Logs` 降级到辅助区或页面下半部分，不与 `Playground / Keys / Logs / Profile` 平级抢焦点。

设计要求：

- 每张动作卡必须像“功能卡片”，而不是普通链接；
- 要有清晰标题、简短说明、图形重心与 hover/focus 状态；
- 视觉上比下半部分信息面板更醒目，但比 Hero 更克制。

### 5.4 Support / Operational Signals

`Actions` 右侧放置辅助列，用于展示轻量“状态与支持信号”，不与主操作区竞争。

建议内容：

- `API Info` 的轻量摘要或入口集合；
- `Uptime` 的轻量摘要；
- `Inspect Task Logs` 等次优先快捷入口。

职责：

- 提供“系统是否正常、有哪些接口入口、遇到问题去哪里看”的低干扰提示；
- 减少用户跳到页面下半部分前的认知落差。

设计要求：

- 采用更紧凑的辅助卡；
- 强调扫读效率；
- 不在这里放长列表与重内容。

### 5.5 Lower Priority Panels

页面下半部分承接次级内容区，统一降级展示：

- `Announcements`
- `FAQ`
- `API Info`
- `Uptime`

该区设计原则：

- 视觉上更克制；
- 信息上更完整；
- 不再试图抢夺首屏注意力。

预期排布：

- 采用 2 列或响应式分组布局；
- 每个面板仍保留现有数据逻辑与交互行为；
- 通过统一容器样式弱化它们之间的视觉割裂。

## 6. 视觉语言

### 6.1 总体风格

整体风格定义为：

- 更精致；
- 更轻盈；
- 更像成熟 SaaS 工作台；
- 避免传统管理后台的硬朗密度感。

### 6.2 背景与色彩

建议延续当前主题 token，不重建整套颜色系统，只在页面层强化层次：

- Hero 使用暖白到冷灰的浅渐变背景；
- 配合 1-2 处柔和高光区，形成工作台氛围；
- 内容卡主要保持白底或浅灰底，靠阴影与边框区分层级；
- 不使用大面积深色块压住首页节奏。

### 6.3 卡片层级

卡片分三档：

- 一级：Hero
- 二级：Summary / Quick Actions
- 三级：Support / Lower Priority Panels

层级表达方式：

- 一级卡更大圆角、更强背景氛围、更明显留白；
- 二级卡有清晰阴影和结构边界；
- 三级卡更克制，强调整洁与可扫读。

### 6.4 交互与动效

保留轻量、有意义的动效：

- 卡片 hover 抬升与阴影变化；
- 按钮 hover/focus 反馈；
- 区块渐进出现的轻量入场。

不引入：

- 无意义的连续动画；
- 轮播；
- 高成本背景特效；
- 任何影响信息读取效率的装饰性动态。

## 7. 组件与代码策略

### 7.1 重构中心

主要重构入口为：

- `web/user-console/src/features/console/index.tsx`

### 7.2 新增展示组件

建议新增 `/console` 专属轻量展示组件，职责单一：

- `console-hero`
- `console-summary-grid`
- `console-action-deck`
- `console-support-column`

这些组件只负责展示结构，不负责取数。

### 7.3 复用现有能力

优先复用如下组件的数据能力与行为：

- `SummaryCards`
- `ApiInfoPanel`
- `AnnouncementsPanel`
- `FAQPanel`
- `UptimePanel`

复用策略：

- 优先保留其现有请求与交互逻辑；
- 如当前外壳样式不适配，可拆出更小的展示层或新增容器封装；
- 避免为了新页面视觉强行修改所有 dashboard 面板的共用样式。

### 7.4 组件边界

组件边界需要满足：

- `Hero` 只处理欢迎区与主 CTA；
- `Summary` 只处理三个核心摘要；
- `Action Deck` 只处理高频功能入口；
- `Support Column` 只处理辅助状态与帮助入口；
- `Lower Panels` 只负责下沉信息区的布局编排。

这样可以保证单一职责，避免一个组件既管布局、又管取数、又管状态判断。

## 8. 响应式与可访问性

### 8.1 响应式

桌面端：

- Hero 左右双栏；
- Summary 三列；
- `Actions + Support` 双栏；
- Lower Panels 两列。

移动端：

- Hero 改为单列堆叠；
- Summary 改为单列或紧凑纵向堆叠；
- Quick Actions 改为单列卡片；
- Support 与 Lower Panels 顺序下沉，确保不出现横向滚动。

### 8.2 可访问性

必须保持：

- CTA 和动作卡的键盘可达性；
- 清晰的标题层级；
- 足够的前景/背景对比度；
- icon-only 行为必须带可访问文本；
- hover 不是唯一状态提示；
- 聚焦态清晰可见。

## 9. 测试与验证

测试目标不是截图级视觉锁定，而是保证结构与主要入口不回退。

至少覆盖：

- `console.test.tsx` 继续验证核心入口仍存在且路由正确；
- 新结构下的主要 CTA 仍可被找到；
- 下沉内容区仍渲染核心面板；
- 页面在移动布局下不出现明显结构性退化。

验证方式：

- `vitest` 组件测试；
- 本地浏览器人工检查 `/console` 页面；
- 如有必要，补一个基础渲染断言，确保新组件拆分不破坏原有文本与链接。

## 10. 风险与取舍

### 10.1 风险

- 如果直接复用 dashboard 面板的外壳样式，页面可能继续显得像“拼装页”；
- 如果 Quick Actions 放太多入口，首屏会失去主次；
- 如果 Hero 承载过多信息，会重新回到旧问题。

### 10.2 取舍

本次重构明确优先：

- 信息主次正确
- 视觉层级清晰
- 展示组件边界干净
- 复用现有数据逻辑

本次不追求：

- 新功能
- 新数据
- 个性化首页
- 图表化工作台

## 11. 最终结论

`/console` 将被重构为一个面向已登录用户的产品化工作台，其核心是：

- 首屏用 `Hero + Summary` 建立欢迎感与账户状态感；
- 中段用 `Quick Actions Deck` 承担主要操作入口；
- 辅助列承接轻量状态与支持信号；
- 公告、FAQ、API 信息、Uptime 全部下沉为次级内容区；
- 全程只做前端展示层重构，复用既有数据逻辑与行为能力。
