# 支持的模型

这个网站本质上是一个多上游 AI 网关，所以“支持哪些模型”分成两个层面：

1. 系统能力层面支持哪些协议和模型类型。
2. 你的当前账号实际能看到、能调用哪些模型。

这两件事不要混为一谈。平台整体支持很多能力，但你最终能用到的模型，仍然以当前账号从 `/api/user/models` 拿到的结果为准。

## 平台能力层面的模型与接口类型

从普通用户的使用角度看，最值得关注的是这些类型：

| 类型 | 说明 |
| --- | --- |
| `OpenAI-Compatible` | 标准 OpenAI 兼容请求格式，例如 `/v1/chat/completions` |
| `OpenAI Responses` | OpenAI Responses 风格接口 |
| `Claude Messages` | Claude 原生消息格式 |
| `Gemini` | Google Gemini 风格接口 |
| `Rerank` | 重排序模型 |
| `Embeddings` | 文本嵌入 |
| `Images` | 图像生成 |
| `Realtime` | 实时会话能力 |

如果你只是接普通应用，大多数情况先从 `OpenAI-Compatible` 或 `OpenAI Responses` 开始就够了。

## 在用户侧你真正能看到什么

前端里有两个地方会直接拉取你当前账号可用的模型：

- `GET /api/user/models`
- `GET /api/user/self/groups`

也就是说：

- 游乐场里的模型下拉，不是写死的。
- API 密钥里的“模型限制”选项，也不是写死的。
- 你在文档里看到的模型示例，不代表你的账号一定能调用。

## 实际查看方式

### 方法一：直接看游乐场

进入 [游乐场](/playground)：

- 模型选择器显示的就是当前账号可以选的模型
- 分组选择器显示的是当前账号可用分组

这是最直观的查看方式。

### 方法二：直接请求模型列表

```bash
curl "<rightmaas_base_url>/v1/models" \
  -H "Authorization: Bearer sk-your-api-key"
```

如果你只是想确认“这个 API 密钥到底能调哪些模型”，这是最直接的外部验证方法。

### 方法三：在创建 Key 时看模型限制选项

进入 [API 密钥](/workspace/keys) 创建或编辑密钥时，“模型限制”里出现的内容也能反映当前账号可见模型范围。

## 常见模型类别示例

下面这些只是平台常见类别示例，不表示你的账号一定全部具备：

- 对话模型：`gpt-4o`、`gpt-4o-mini`、`claude-*`、`gemini-*`
- 代码模型：`codex-*`、`deepseek-coder-*`
- 嵌入模型：`text-embedding-*`
- 图像模型：`dall-e-*` 或其他图像上游映射模型

## 关于带后缀的模型名

有些模型会通过名字后缀表达特殊行为，例如：

- 推理强度后缀
- thinking / nothinking 后缀
- 预算相关后缀

因此当你看到一个模型名很长时，不要急着把它当成“拼错了”，它有可能是平台约定的一种能力开关。

## 为什么我的账号看不到别人文档里的模型

最常见的原因有：

1. 管理员没有把该模型开放给你的用户组。
2. 你的密钥设置了“模型限制”。
3. 某个分组下没有对应可用通道。
4. 模型虽然平台整体支持，但当前实例并没有实际配置该上游。

## 选择模型时的建议

- 第一次联调：优先选价格较低、稳定性高的小模型。
- 做正式接入：先确认目标模型是否能稳定在你的目标分组上使用。
- 做权限隔离：通过“模型限制”把不同密钥的模型范围拆开。

## 一条最实用的判断原则

文档和页面说明都只能作为参考。

**最终以这三个事实为准：**

1. 游乐场里是否能选到。
2. `/v1/models` 是否能返回。
3. 实际请求是否能在 [请求日志](/workspace/logs) 中成功落日志。
