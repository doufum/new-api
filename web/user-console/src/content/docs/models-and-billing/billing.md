# 计费说明

网站的用户侧计费入口主要集中在 [钱包](/account/wallet) 和 [请求日志](/workspace/logs)。如果你只需要知道“我还能不能继续调用、花了多少、去哪里补余额”，这份文档足够直接。

## 你需要关心的三个位置

| 页面 | 路径 | 主要用途 |
| --- | --- | --- |
| 钱包 | `/account/wallet` | 查看余额、充值、兑换充值码、查看账单 |
| 使用日志 | `/workspace/logs` | 查看每次请求的用量、模型、分组、失败原因 |
| API 密钥 | `/workspace/keys` | 查看某个密钥是否还有单独额度限制 |

## 钱包里现在有哪些能力

根据系统配置，钱包页可能会展示以下能力中的一部分：

- 在线充值
- Stripe 充值
- Creem 支付
- Waffo 支付
- Waffo Pancake 支付
- 充值码兑换
- 账单历史
- 订阅套餐与扣费顺序

前端会根据后端配置动态显示可用方式，所以你在自己实例里看到的项目数可能和别人的环境不同。

## 充值的实际流程

进入 [钱包](/account/wallet) 后，一般会按这个顺序操作：

1. 选择或输入充值金额。
2. 查看当前支付方式是否满足最低充值金额。
3. 选择一个可用支付方式。
4. 确认支付金额后跳转到对应结算页。

注意两点：

- 不同支付方式可能有不同的最低充值门槛。
- 某些支付方式只在管理员启用后才会出现在页面。

## 充值码兑换

如果管理员提供了充值码，可以直接在钱包页输入后兑换。兑换成功后，建议立即刷新观察：

- 当前余额
- 账单历史
- 后续请求是否恢复正常

这通常是处理“测试环境临时补额度”最快的方式。

## 订阅与扣费顺序

如果当前网站启用了订阅能力，你可以在钱包页看到：

- “订阅套餐”
- “我的订阅”
- 扣费顺序相关选项

常见场景是：

- 选择“优先订阅”时，系统会优先消耗订阅权益
- 选择“仅用订阅”时，系统会尽量只使用订阅额度

如果你在日志里看到扣费结果和预期不同，先检查自己是否已经启用了订阅，以及当前选择的扣费顺序是什么。

## 请求日志怎么看计费

在 [请求日志](/workspace/logs) 中，“通用日志”最适合排查费用与模型消耗。你可以重点看这些字段：

- 模型名
- 分组
- 输入 Token
- 输出 Token
- 请求类型
- 错误详情
- 明细弹窗中的计费信息

如果开启了更详细的日志能力，明细里还可能出现：

- 模型倍率
- 分组倍率
- 用户组倍率
- 是否按次计费
- 缓存 Token 相关数据

## 为什么余额充足但还是失败

常见原因包括：

1. 不是账户总余额不足，而是某个 API 密钥自己的额度耗尽。
2. 当前模型或分组没有可用上游。
3. 请求被速率限制拦住了。
4. 你命中了订阅或计费策略限制，而不是单纯余额问题。

所以不要只看钱包余额，最好结合：

- [API 密钥](/workspace/keys)
- [使用日志](/workspace/logs)

一起判断。

## 一个建议的排查顺序

当你怀疑“为什么这次请求收费了 / 没收费 / 扣费异常”时，建议按这个顺序看：

1. 到 [请求日志](/workspace/logs) 找到对应请求。
2. 查看模型、分组、Token 和错误信息。
3. 打开明细弹窗确认是否有倍率、订阅或按次计费信息。
4. 再回到 [钱包](/account/wallet) 看余额、账单历史和订阅状态。

## 使用建议

- 正式环境不要只依赖“总余额”，最好同时给关键 API 密钥设置额度边界。
- 测试环境优先使用小额度、短周期的 API 密钥。
- 如果你的团队多人共用站点，建议每个系统拆分单独 API 密钥，这样在日志和账单上更容易追踪消耗来源。
